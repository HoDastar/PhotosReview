# proj.html 评分满分从固定 4 改为自定义的可行性分析

## 结论
可行，且改造成本中等偏低。当前前后端都把评分上限“写死”为 4，需要同时改前端展示/交互与后端校验。

## 现状（固定 4 分的落点）
1. 前端 `proj.html`：评分单选按钮硬编码为 1、2、3、4。
2. 前端 `proj.js`：快捷键 `q/w/e/r` 分别映射 1~4 分。
3. 后端 `ReviewAPI.submitPhotos`：仅允许 `1~4`，条件为 `score <= 0 || score >= 5`。

## 可选方案

### 方案 A：全局设置（系统统一评分上限）
- 做法：在系统配置中增加 `score_max`（例如 4~10），`proj.html` 前端拉取并动态渲染单选项，`submit` 按全局值校验。
- 优点：实现快、改动面最小。
- 缺点：所有项目共享上限，不适合项目评分标准差异较大场景。

### 方案 B：按工程设置（推荐）
- 做法：在项目表（`EntityReviewProj` 对应数据）新增字段如 `scoreMax`；创建/编辑项目时可配置；`/api/proj/get_proj` 与 `fetch_photo_list` 返回该值；前端按项目动态渲染评分项；后端提交按该项目配置校验。
- 优点：灵活，符合多项目并行管理；兼容“审片/筛片”不同策略。
- 缺点：需做一次数据库迁移与管理端配置页面改造。

## 为什么推荐“按工程设置”
- 现有系统天然以 `proj` 为任务/权限/状态边界，评分规则属于项目业务规则，放在项目维度更一致。
- 未来若出现不同业务线（如质检项目 5 分、创意项目 10 分）可直接支持。

## 实施建议（按工程）
1. **数据层**
   - 项目表新增 `score_max`（默认 4，NOT NULL）。
   - 实体与 Mapper 增加字段映射。
2. **接口层**
   - `get_proj`、`fetch_photo_list` 响应中返回 `scoreMax`。
   - `submit` 校验改为：`1 <= score <= scoreMax`。
3. **前端层**
   - `proj.html` 的固定 radio 改为容器；在 `proj.js` 根据 `scoreMax` 动态生成 1..N。
   - 快捷键：保留 `qwer` 对应 1~4；对 5+ 分建议增加数字键（`5..9,0`）或 `[`/`]` 调分。
4. **兼容性**
   - 旧项目无该字段时回退到 4（后端兜底）。
   - 历史数据 score 不变，因新范围是扩展，不影响读取。

## 工程级 vs 全局的最终建议
- 默认采用**按工程设置**。
- 可额外提供“系统默认值（全局）”作为新建项目默认 `score_max`，兼顾易用性与灵活性。
